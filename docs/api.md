# API NewDay: что за что отвечает

Машинное описание — `GET /api/v1/openapi.json`: там все шестьдесят шесть путей с
телами запросов и кодами ответов, его понимают Swagger, Postman, Insomnia и
генераторы клиентов. Здесь другое: зачем каждая группа путей нужна и чем они
отличаются друг от друга. Это то, чего в спецификации не написать.

Основа — `https://newday.appswire.ru/api/v1`.

## Токен

Токен выпускается в шторке **«Аккаунт»**, внизу, кнопкой «Выпустить токен».
Показывается он один раз: сервер хранит только его хеш, и «показать ещё раз»
невозможно даже ему. Не сохранили — «Перевыпустить»: старый перестаёт
действовать, новый показывается снова.

```
Authorization: Bearer nd_a1b2c3d4_xxxxxxxxxxxxxxxxxxxxxxxx
```

Две области: `read` видит всё, но ничего не меняет; `write` — меняет. Из шторки
выпускается `write` — токен нужен, чтобы что-то записывать, иначе он бесполезен;
`read` доступен через API, если хочется отдать что-то только на чтение.

**Чего токен не умеет нарочно:** выпускать другие токены, привязывать
устройства и менять пароль. Эти пути требуют именно браузерной сессии. Утёкший
токен даёт доступ к данным, но не к аккаунту, — и отзывается одной кнопкой.

Токен устройства (`ndd_…`) — другой: его получает Android-приложение при
привязке по QR-коду, и живёт он в списке «Устройства». `GET /devices` отдаёт
у каждого устройства `lastIp` — последний адрес, с которого оно приходило:
по нему в списке одинаковых имён можно опознать чужака. Если при входе из
приложения имя устройства пустое или голое «Android», сервер подставляет
модель из User-Agent («Pixel 7», «SM-A536E»).

## Общие правила

**Дата — строка `YYYY-MM-DD` в таймзоне человека, а не в UTC.** Это важнее, чем
кажется: «сегодня» у пользователя в Москве и у сервера в Амстердаме — разные
дни, и `new Date().toISOString()` в клиенте однажды сдвинет всё на сутки.
Правильное «сегодня» отдаёт `GET /settings` в поле `today`.

**Время внутри дня — минуты от полуночи.** `540` это 09:00. Никаких строк
«09:00» в ответах: минуты складываются, сравниваются и сортируются, а строки
приходится разбирать.

**`endMin: null` — это момент, а не отрезок.** Так выглядит напоминание. Отдельной
сущности «напоминание» нет: это строка расписания с `kind: "reminder"` и пустым
концом.

**Отказ приходит телом,** а не пустым 400:

```json
{ "error": { "code": "VALIDATION", "message": "Поле «конец» должно быть целым числом от 0 до 1439" } }
```

`message` написан по-русски и годится, чтобы показать человеку как есть.

**Одновременная правка.** Полная запись дня требует заголовка `If-Match` с
текущим `rev`:

```
If-Match: "7"
```

Не совпало — 409 `REV_MISMATCH`, и в теле лежит актуальный день: есть чем
разрешить расхождение. Забыли заголовок — 428. Правка отдельной строки
`If-Match` не требует; если прислать `updatedAt`, сервер ответит 409
`STALE_ROW`, когда строку успели поменять.

## День и то, что в нём

| Путь | Зачем |
|---|---|
| `GET /days/{date}/full` | всё про день одним запросом: расписание, задачи, питание, спорт, привычки на этот день, прогресс. `rev: 0` значит «дня ещё нет» |
| `PUT /days/{date}/full` | заменить день целиком. Нужен `If-Match` |
| `GET /days/{date}` | только поля дня, без вложенных списков |
| `PATCH /days/{date}` | заголовок, фокус, вес, заметка, план питания. Нужен `If-Match` |
| `GET /days/range?from&to` | расписание и счётчики за период — для сеток недели и месяца |
| `POST /days/{date}/copy-to` | скопировать день в другую дату. Отметки выполнения не переносятся: это план, а не факт |

`GET /days/range` существует отдельно нарочно: тянуть тридцать полных дней ради
тридцати клеток месяца — это тридцать лишних расчётов статистики.

**Строки дня** — четыре списка с одинаковым набором путей:

```
GET    /days/{date}/schedule        список
POST   /days/{date}/schedule        добавить
PATCH  /days/{date}/schedule/{id}   изменить
DELETE /days/{date}/schedule/{id}   удалить
POST   /days/{date}/schedule/reorder  { ids: [...] }
```

То же для `tasks`, `meals`, `sport`. Порядок задаёт сервер и он же его отдаёт —
клиент не может разойтись с базой.

Поля строки расписания: `startMin`, `endMin`, `title`, `note`, `kind`,
`alarmMode`, `alarmProfile`, `remindBefore`, `color`, `done`. Время можно
прислать и строкой: `time: "9:30-13"` — разберётся, включая «930» и «19».

Два своих пути у расписания:

- `POST /days/{date}/schedule/shift` — сдвинуть строку и, при `cascade`, всё,
  что начинается не раньше. Сценарий «задержался на обеде на пятнадцать минут».
- `POST /days/{date}/schedule/{id}/series` — привязать строку к повтору или
  отвязать (`{ seriesId: null }`). Привязанная строка говорит серверу, что этот
  день повтором уже достроен; без этого появлялась бы вторая такая же.

## Повторы и шаблон дня

Одна таблица `series`, два смысла, и разделяет их наличие имени:

- **правило без имени — повтор.** Сервер сам достраивает им дни при первом
  чтении: `freq` = `daily` | `weekly` | `monthly` | `yearly`, плюс `interval`,
  `byweekday` (битовая маска, бит 0 — понедельник), `startDate`, `endDate`;
- **правило с именем — шаблон дня.** Применяется вручную
  (`POST /series/{id}/apply`) или сам заполняет пустой день.

Разделяет их в списке `?templates=1` / `?templates=0`.

Удаление правила: без параметров правило уходит вместе с будущими строками, а
прошлые остаются — они часть прожитых дней. С `?from=YYYY-MM-DD` правило
получает дату окончания, и прошлое не трогается вовсе.

## Привычки

Привычки живут отдельно от дней: у них своя таблица и свой журнал отметок.
Поэтому `PUT /habits/{id}/log/{date}` — не поле `done` в дне, а запись за дату
со статусом `done` | `missed` | `skipped`.

`GET /habits/{id}/stats` считает серии, проценты и прогресс челленджа с учётом
графика: у привычки «трижды в неделю» пропущенный вторник — не пропуск, и
считать его таковым значило бы врать человеку про его же серию.

Удаление — в архив: журнал отметок это история, и стирать её вместе с привычкой
значит переписывать прошлое. `?hard=1` удаляет насовсем, `POST
/habits/{id}/restore` возвращает.

## Заметки

`/notes` — только заметки **без даты**. Заметка с датой — это поле `notes`
самого дня, и правится через `PATCH /days/{date}`. Вид определяется датой,
поэтому одна и та же заметка не может лежать в двух местах.

## Уведомления

Планировщик считает очередь сам, из строк дня: `alarmMode` ≠ `none` и список
`remindBefore` дают по записи на каждый срок. Клиенту остаётся подписаться:

1. `GET /push/key` — открытый ключ VAPID;
2. `POST /push/subscribe` — подписка из `PushManager`;
3. `GET /push/status` — что подписано и что в очереди на ближайшее время.

`POST /push/replan` пересчитывает сегодня и завтра — им пользуется само
приложение после правок. `POST /push/test` присылает проверочное.

В `remindBefore` можно передать `-1` — это «к концу», а не «за минус одну
минуту»: срок считается от `endMin` строки. Так работает «к концу окна» у
приёма пищи.

## Свои звуки будильника

Встроенных мелодий мало, а просыпаться приятнее под свою. Звук хранится на
сервере, а не в браузере: браузерное хранилище живёт до первой чистки, и
будильник, потерявший мелодию за ночь, — это проспанное утро. Заодно звук
доступен с любого устройства под тем же аккаунтом.

| Путь | Зачем |
|---|---|
| `GET /sounds` | список: `[{ id, name, mime, sizeBytes, createdAt }]` |
| `POST /sounds` | загрузить: multipart с полем `file` и необязательным `name`. Без `name` имя берётся из имени файла без расширения. Ответ — та же форма, что в списке |
| `GET /sounds/{id}/file` | сам файл — с верным `Content-Type`, годится прямо в `src` тега `audio` |
| `DELETE /sounds/{id}` | удалить: `{ success: true }` |

Принимаются mp3, ogg, wav и m4a/aac (`audio/mpeg`, `audio/ogg`, `audio/wav`,
`audio/mp4`, `audio/aac`, `audio/x-m4a`) — то, что умеют играть браузер и
Android. Лимиты: файл до 10 МБ — это десять минут звука в хорошем качестве,
дольше будильник не звонит; до 20 звуков на пользователя — это уже набор
будильников, а не фонотека. Превышение — обычный 400 с объяснением по-русски.

Файл отдаётся с `Cache-Control: private, max-age=3600`: кешировать можно, но
только себе — звук загружен под аккаунтом, и общий кеш отдал бы его чужому.
Чужой `id` во всех путях отвечает 404, как будто звука нет вовсе.

`GET /export` отдаёт всё: дни, строки, задачи, питание, спорт, привычки с
журналом, правила повторов и шаблон, отметки дней, заметки без даты. Тот же
формат вливается обратно через `POST /import` в режиме `merge` (не трогает дни,
которые уже есть) или `replace` (заменяет всё).

`GET /export.ics` — расписание в iCalendar, его понимает любой календарь.
`?from` и `?to` ограничивают период; по умолчанию месяц назад и всё вперёд.

## Помощник

`POST /ai/parse` разбирает текст в пункты плана, `POST /ai/improve` предлагает,
чем дополнить день, `POST /ai/transcribe` расшифровывает надиктованное
(multipart). Работает, только если администратор включил помощника и задал
ключ, — проверить это можно через `GET /ai/status`, который отвечает
`{ ready, voice }`. `voice` отвечает отдельно, потому что распознавание —
отдельное подключение (см. «Админка»): текст может работать, а речь нет.

## Админка

Панель администратора живёт на `/api/admin/*` и входит по паролю экземпляра,
а не по пользовательскому аккаунту: `POST /api/admin/login { password }` ставит
админскую отметку в сессию на 12 часов и отвечает `{ ok, mustChangePassword }`.
Пока пароль не сменён с дефолтного «newday» (`POST /api/admin/password
{ current, next }`), каждый вход напоминает об этом. Пять неверных паролей
подряд — 429 на четверть часа. `POST /api/admin/logout` гасит только админскую
отметку.

Внутри: `GET|PATCH /settings` — флаги `registrationOpen`, `aiEnabled`
(рубильник помощника) и `defaultAiTier` — тариф помощника для регистрации
без приглашения (код приглашения этот выбор перекрывает); `GET|POST
/invites` и `DELETE /invites/{id}` — приглашения с пределом использований
и тарифом помощника для новичка (ссылка вида `/register.html?invite=<код>`);
`GET /users` и `PATCH /users/{id} { aiTier }` — люди и их тарифы (`off |
limited | unlimited`, у limited — 50 обращений в сутки по часам
пользователя); `GET|PATCH /ai` — подключение модели (ключ наружу не
отдаётся) и список прокси, `POST|PATCH|DELETE /ai/proxies` — сами прокси
(http, https и socks5; socks5 ходит через `socks5h`, то есть имена
резолвятся на прокси), `POST /ai/check` — живой пинг; `GET /stats` —
люди, расход помощника по дням и краткое здоровье сервера.

### Два подключения: текст и речь

Распознавание речи ходит своим адресом и своим ключом. Текст дешевле взять
у агрегатора, а whisper — у того, кто его умеет, и это разные ключи. Пустой
`voiceBaseUrl` или пустой `voiceApiKey` означают «то же, что у текста»: каждое
поле подставляется само по себе, так что можно сменить только ключ, оставив
адрес общим. Поэтому уже настроенные установки ничего не замечают, и заполнять
второй раз одно и то же большинству не нужно. Прокси общие: они про сеть, а не
про провайдера.

`GET /ai` отдаёт по речи: `voiceModel`, `voiceBaseUrl` (уже с подстановкой —
то, куда запросы уйдут на самом деле), `voiceKeySet`, `voiceKeyTail`
(последние 4 символа действующего ключа), `voiceOwn` (заданы ли свои адрес
или ключ — иначе показанное является отражением текстового) и `voiceReady`.
Сам ключ не отдаётся никогда.

`PATCH /ai` принимает `voiceBaseUrl`, `voiceApiKey` и `voiceModel` по тем же
правилам, что `baseUrl`/`apiKey`: пустая строка ключа — «не менять» (форма его
не показывает и не должна затирать при каждом сохранении), `null` — «стереть»,
то есть вернуться к текстовому. Пустая строка в `voiceBaseUrl` — тоже возврат
к текстовому адресу. Адрес без `http://` или `https://` — 400 `BAD_URL`.

`POST /ai/check` принимает необязательное `{ what: 'text' | 'voice' }`, по
умолчанию `'text'`. Ответ — `{ ok, what, latencyMs }` или `{ ok: false, what,
error }` с причиной по-русски. Текст проверяется маленьким настоящим запросом
к модели, речь — списком моделей (`GET {voiceBaseUrl}/models`): расшифровка
тарифицируется по секундам, и кнопка не должна тратить деньги. Если список
пришёл, но выбранной модели в нём нет, ответ остаётся `ok: true` и добавляется
`warning`. Провайдер без `/models` (404/405) честно получает `ok: false` с
объяснением, что проверить нечем, — надиктуйте что-нибудь. Оба пинга идут теми
же прокси, что и рабочие запросы.

Удаление пользователя двухступенчатое. `POST /users/{id}/block` закрывает
доступ: все запросы человека и вход по паролю отвечают 403
`ACCOUNT_BLOCKED`, но данные, сессии и токены целы — `POST
/users/{id}/unblock` возвращает всё как было. `DELETE /users/{id}` стирает
аккаунт насовсем со всеми данными и работает только по уже заблокированному
(иначе 400): между обратимым и необратимым шагами обязана стоять пауза.
Заблокированные дольше 60 дней стираются автоматически — в списке
`GET /users` у каждого есть `blockedAt` (null, если не заблокирован) и
`deleteAfter` — дата будущей автоочистки.

Публично, без входа: `GET /api/v1/auth/config` → `{ registrationOpen,
aiEnabled }` — страница входа по нему решает, показывать ли регистрацию.
Когда регистрация закрыта, `POST /auth/register` требует поле `invite`
с живым кодом.

## Наблюдение за сервером

`GET /api/health` — без версии и без входа, для Uptime Kuma и подобных.

**Подробности закрываются ключом.** «Жив или нет» остаётся открытым: наблюдалке
нужен код ответа, и требовать ключ ради того, что видно по доступности сайта,
незачем. А версия схемы, длина очереди и причины поломки рассказывают о
внутренностях — их отдаёт только запрос с ключом. Ключ выпускается в админке,
в разделе «Настройки», и показывается один раз: сервер хранит хеш. Прислать
его можно тремя способами — у наблюдалок разные привычки:

```
X-Health-Token: <ключ>
Authorization: Bearer <ключ>
/api/health?token=<ключ>
```

Пока ключ не выпущен, подробности открыты: сервер, поднятый пять минут назад,
должен уметь объяснить, что с ним не так, до всякой настройки. Отзыв ключа
возвращает это состояние.
 Пока
всё в порядке — 200 и `{ ok: true }` с подробностями: пишется ли база, все ли
миграции накатаны, стоит ли очередь уведомлений, включены ли почта, помощник и
уведомления. Что-то сломалось — 503, и в `problems` лежат причины словами:
«База не принимает запись…», «Очередь уведомлений стоит: самое старое опоздало
на 14 мин…». В наблюдалке достаточно проверять код ответа, а причину читать из
тела, когда загорится.

Уведомление, окончательно упавшее на мёртвой подписке, аварией не считается —
иначе одна протухшая браузерная подписка держала бы «сайт красный» на живом
сервере.

## Быстрая проверка, что токен живой

```bash
TOKEN=nd_...
BASE=https://newday.appswire.ru/api/v1

# кто мы и какое сегодня по нашей таймзоне
curl -s -H "Authorization: Bearer $TOKEN" "$BASE/settings" | jq '{email, timezone, today}'

# день целиком
curl -s -H "Authorization: Bearer $TOKEN" "$BASE/days/2026-08-06/full" | jq '.schedule[] | {start_min, end_min, title}'

# добавить блок
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"time":"09:00-10:30","title":"Работа над отчётом","alarmMode":"notify"}' \
  "$BASE/days/2026-08-06/schedule"

# добавить напоминание — тот же путь, конец пустой
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"startMin":900,"endMin":null,"title":"Забрать документы","kind":"reminder","alarmMode":"notify"}' \
  "$BASE/days/2026-08-06/schedule"
```
