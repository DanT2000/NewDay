# Местная копия дня и очередь правок

Дата: 2026-09-19. Статус: одобрено в диалоге (вариант А — очередь правок на
устройстве, местная копия как источник для отрисовки).

## Зачем

Две жалобы, у которых одна причина.

Первая: «пока отправится, пока придёт, потом только отрисуется». Сейчас
почти каждая правка проходит через `busy()` в [app.js](../../../public/js/web/app.js):
кнопка встаёт в «Сохраняю…», экран ждёт ответ сервера, и только потом шторка
закрывается. На мобильной сети это полсекунды-полторы на каждое нажатие.
Мгновенно применяются только галочки — через `optimistic()` в
[store.js](../../../public/js/web/store.js).

Вторая: без связи правки не сохраняются вовсе. `optimistic()` откатывает
галочку назад, `busy()` показывает ошибку, а через весь экран висит полоса
«Нет связи… появится связь — повторите». Человек отмечает дело в метро,
видит, как галочка отскакивает обратно, и возвращается к этому вечером.

Нужен один и тот же путь для обоих случаев: правка применяется на устройстве
сразу, а отправка — фоновая работа, которая идёт своим темпом и переживает
и отсутствие связи, и закрытие приложения.

## Принцип

**То, что на экране, — это последний ответ сервера плюс все ещё не уехавшие
правки, наложенные по порядку.**

Из этой формулировки следует всё остальное:

- наложение правки — чистая функция, её можно повторить сколько угодно раз;
- перечитывание дня с сервера не «съедает» правку, которая ещё в очереди:
  после загрузки проекция считается заново;
- очередь переживает перезапуск приложения, потому что лежит в localStorage
  рядом с местной копией дня;
- порядок отправки строго тот же, в котором человек нажимал: создать →
  изменить → удалить не могут разъехаться.

## Части

### 1. `public/js/outbox.js` — очередь

Новый модуль без DOM и без знания о дне: он умеет хранить, отправлять и
рассказывать о состоянии. Проверяется обычными node-тестами.

Хранение: `localStorage['newday.outbox.v1']` = `{ v: 1, ops: [...] }`.

Операция:

```js
{
  id: 'op-3f2a…',    // он же ключ идемпотентности
  at: 1758270000000, // когда человек нажал
  вид: 'задача.создать',
  дата: '2026-09-19',
  цель: 'tmp-1' | 17, // id строки: временный или настоящий
  данные: { … },      // тело запроса
  попытки: 0,
  ошибка: null,
}
```

Наружу:

- `добавить(оп)` — кладёт в конец, будит отправку;
- `ожидает()` — сколько правок ещё не уехало;
- `конфликты()` — что сервер отверг;
- `отправить()` — прогнать очередь;
- `подписаться(fn)` — сообщить экрану, что число изменилось;
- `забыть(id)` / `повторить(id)` — для панели «не доехали».

**Отправка строго по одной, по порядку.** Разбор ответа:

| Ответ | Что делаем |
|---|---|
| Успех | убираем из очереди, запоминаем настоящий id |
| Нет связи (`NETWORK`) | останавливаем прогон, ждём следующего повода |
| 401 | останавливаем всё: нужен вход, очередь не теряем |
| 404 на удаление | считаем успехом: уже удалено |
| 4xx (400/404/409/422) | операция в «не доехали», прогон продолжается |
| 5xx | до трёх попыток с нарастающей паузой, потом в «не доехали» |

Поводы к отправке: запуск приложения, каждое добавление, событие `online`,
возврат приложения на экран, таймер с нарастающей паузой (2 с → 4 → 8 →
… → 60 с), пока очередь не пуста.

**Временные id.** Создание получает `tmp-1`, `tmp-2` — с ними строка живёт на
экране. Ответ сервера даёт настоящий id; подстановка проходит и по очереди
(последующие правки той же строки), и по местной копии дня.

**Две вкладки.** Очередь в localStorage общая, поэтому перед прогоном вкладка
берёт аренду `newday.outbox.lock = { tab, until }` на 20 секунд и перечитывает
очередь из хранилища перед каждой операцией. Событие `storage` говорит другой
вкладке перерисовать значок. Даже если аренда разъедется (вкладка уснула),
ключ идемпотентности не даст создать вторую строку.

**Предел.** 500 операций. Дальше очередь не принимает новые и говорит об этом
прямо: это значит, что связи нет очень давно и дело не в очереди.

### 2. `public/js/web/apply.js` — наложение

Чистая функция `наложить(день, оп) → день` и `наложитьВсе(день, ops)`. Знает
про каждый вид операции и больше ни про что: ни сети, ни localStorage, ни DOM.
Отсюда её легко проверить и невозможно сломать порядком вызовов.

Прогресс дня (`progress()` в app.js) и так считается на клиенте по строкам,
поэтому плитки «завершено сегодня» обновятся сами.

### 3. `store.js` — правки через очередь

Функции правок дня перестают быть обёртками над `api.*` и становятся:
наложить на `store.day` → сохранить местную копию → положить в очередь.
`loadDay()` после ответа сервера накладывает оставшиеся операции поверх
свежего дня — иначе правка мигала бы и исчезала на время полёта.

### 4. `app.js` — экран не ждёт сеть

`busy()` остаётся для операций, которым связь нужна (см. ниже). Для правок дня
появляется `сразу(job)`: применили, закрыли шторку, нарисовали — без «Сохраняю…».

Полоса «Нет связи» на весь экран уходит. Вместо неё — маленький постоянный
значок в шапке:

- связь есть, очередь пуста — значка нет;
- есть неотправленное — «⟳ 3»;
- связи нет — «Нет связи · 3»;
- есть «не доехавшие» — значок заметный, по нажатию открывается список.

Список «не доехали» — обычная шторка: что за правка, почему не сохранилась
по-человечески («эту задачу уже удалили на другом устройстве»), кнопки
«Повторить» и «Забыть».

**Составные действия.** Несколько мест сейчас ждут ответ сервера, чтобы взять
из него id: приём пищи с блоком в расписании (`block.id` → `scheduleItemId`),
перенос строки на другую дату (создать там, удалить здесь). Они переписываются
на местный id: строка создаётся в местной копии сразу и уже имеет `tmp-N`, а
подстановку настоящего номера делает очередь. Никакой отдельной логики
ожидания в app.js не остаётся.

### 5. Сервер — защита от двойного создания

Одна таблица, миграция 015:

```sql
CREATE TABLE op_keys (
  user_id INTEGER NOT NULL,
  key     TEXT    NOT NULL,
  status  INTEGER NOT NULL,
  body    TEXT,
  created_at TEXT NOT NULL,
  PRIMARY KEY (user_id, key)
);
```

Заголовок `Idempotency-Key` учитывается **только на POST создания строк дня**
(расписание, задачи, еда, спорт). PATCH с полными значениями и DELETE
идемпотентны сами по себе. Повторный запрос с тем же ключом отдаёт
сохранённый ответ и ничего не создаёт. Чистка старше суток — рядом с уже
существующей часовой уборкой в [server/index.js](../../../server/index.js).

## Что уходит в очередь, а что требует связи

Офлайн (ежедневная работа):

- галочки: строка расписания, задача, еда, подход, привычка;
- создать / изменить / удалить: задачу, строку расписания, приём пищи, подход;
- поля дня: заметка, вес, план питания;
- настройки приложения (тема, акцент, переключатели) — иначе они отскакивают.

Требуют связи, как сейчас (кнопка честно говорит, что нужна связь):

- повторы и шаблоны, применение шаблона к дню, копирование дня, сдвиг
  блоков каскадом — их считает сервер, и повторять эту логику на клиенте
  значит завести вторую правду;
- привычки как сущности (создать, переименовать, архивировать) — редкая
  операция, и она глобальная, а не про день;
- помощник, отчёты, звуки, устройства, токены, выгрузка.

Серия привычек (`habitsStreak`) приходит с сервера и офлайн останется
прежней до синхронизации. Это честнее, чем считать её на клиенте по
неполным данным.

## Конфликты

Правило одно: **побеждает тот, чья правка доехала позже.** Для дневника это
верно — человек один, устройств два, и правка с телефона по дороге домой
должна лечь поверх утренней с компьютера.

Явный конфликт человек видит только тогда, когда сервер отказал совсем:
строку удалили на другом устройстве, день не проходит проверку, сервер
вернул 409. Тогда правка попадает в «не доехали», день перечитывается, и
человек решает сам. Никаких «сохранить обе версии» и никакого слияния
текста — этого в дневнике не нужно.

## Проверки

Node-тесты (`test/web/`):

- очередь: порядок, остановка на `NETWORK`, продолжение после 4xx, три
  попытки на 5xx, подстановка временного id в последующие операции, предел
  в 500, аренда между вкладками, переживание перезапуска;
- наложение: по одному тесту на вид операции плюс «сервер ответил, а в
  очереди ещё две правки — проекция сохраняет обе».

API-тесты (`test/api/`):

- два POST с одним `Idempotency-Key` создают одну строку и дают один ответ;
- ключ чужого пользователя не виден;
- чистка старых ключей.

Живые пробы (`tools/web-live-check.mjs`, они же в CDP-браузере):

- офлайн: отметить дело, добавить задачу, изменить время блока → всё видно
  сразу, значок показывает «3»;
- перезагрузка страницы с непустой очередью → правки на месте;
- связь вернулась → очередь уехала, значок исчез, сервер отдаёт те же данные;
- две вкладки офлайн, обе правят день → после связи ни дублей, ни потерь;
- правка строки, удалённой на другом устройстве → она в «не доехали», а не
  молча потеряна.

## Чего не делаем

- слияния текста и истории версий;
- Background Sync и отправки при закрытом приложении: у нас нет служебного
  процесса, а обещать доставку «в фоне» и не выполнить — хуже, чем не
  обещать;
- офлайн-помощника и офлайн-отчётов;
- журнала изменений на сервере и инкрементальной синхронизации: при двух
  устройствах перечитать день дешевле, чем содержать вторую механику.

## Риски

- **Расхождение экрана и сервера.** Страховка — проекция как чистая функция:
  после любой загрузки она считается заново, и накопленная ошибка невозможна.
- **Разрастание app.js.** Он и так большой. Очередь и наложение живут
  отдельными файлами, в app.js добавляется только значок и шторка «не доехали».
- **Половинчатые сценарии** (создать строку офлайн и тут же привязать к ней
  повтор): повторы требуют связи, поэтому кнопка будет недоступна, пока
  строка не уехала. Это видно человеку и честно.
